    TL;DR

    For 48 minutes on 2026-10-14 the dispatcher assigned no export.v2 steps to worker-3. The scheduler resumed worker-3's session after a disconnect but never asked it to re-publish its capabilities, so the registry listed worker-3 with zero capabilities.

    What
    export-render backlog grew from 5 to 197 steps. P99 step wait reached 5m 30s against a 2m SLO.
    Cause
    Session resumption, added in scheduler v4.18.0, returns before requestCapabilities. A disconnect had already cleared worker-3's capabilities.
    Mitigation
    On-call restarted worker-3 at 14:34:40. The new session re-published 14 capabilities, and the queue reached baseline at 14:50.
    Fix
    Call requestCapabilities on the resume path, add a reconnect test, and alert on live workers with zero capabilities.

    Context

    Scheduler v4.18.0 rolled out to prod-east at 13:58 R1. The release added session resumption: a worker that reconnects within 60s keeps its session instead of registering again R2. The session lifecycle doc does not mention capability publication R3.

    The rollout restarted scheduler-2, which dropped worker-3's stream. worker-3 reconnected to scheduler-1 eighteen seconds later and resumed its session R4. From 14:02:31 the dispatcher filtered worker-3 out of every export.v2 candidate list R5. worker-1 and worker-2 ran at capacity, and the queue grew by about 6 steps per minute until the depth alert fired at 14:22 R6.

    Scope

    Only worker-3 resumed a session during the rollout. worker-1 and worker-2 were connected to scheduler-1, which restarted last, and both registered fresh sessions R4. No other workflow pinned to worker-3 had steps queued in the window.

    Findings

    Root causeResumed sessions skip capability publication

    handleConnect in scheduler/session.go returns on the resume path before it calls requestCapabilities. A disconnect clears the worker's capabilities from the registry, so a resumed worker stays connected and healthy with an empty capability list.

    Evidence 1: logs

    Between the resume at 14:02:05 and the restart at 14:34:40 the logs have no capabilities published line for worker-3 R4. A fresh registration logs one within a second.

    Evidence 2: code

    PR #1412 added the early return R2. Before it, every connect created a new session and called requestCapabilities.

    scheduler/session.go:88go
    func (c *Scheduler) handleConnect(req *ConnectRequest) (*ConnectAck, error) {
    if sess, ok := c.sessions.Resume(req.SessionID); ok {
        c.log.Info("session resumed", "worker", req.WorkerID, "session", sess.ID)
        return sess.Ack(), nil
    }
    sess := c.sessions.New(req.WorkerID)
    c.requestCapabilities(sess)
    return sess.Ack(), nil

    Detection gap

    Queue depth lags the cause. The alert fired 20 minutes after worker-3 dropped out. A connected worker with zero capabilities is detectable within one reconcile pass, but nothing alerts on it today.

    Remediation and next steps

    Mitigation

    • Restarted worker-3 at 14:34:40 to force a new session R8.
    • Checked every prod-east worker's capability count against its manifest. No other worker was affected.
    • Paused the v4.18.0 rollout to prod-west and prod-apac.

    Fix

    1. Call requestCapabilities on the resume path. A resumed session may outlive a registry clear, so publication has to happen on every connect.
    2. Add TestResumeRepublishesCapabilities: disconnect a worker, resume its session, and assert the registry's capability count is restored.
    3. Alert when a worker has a live heartbeat and zero capabilities for more than 2 minutes. This catches the condition at the source instead of at the queue.
